# Week 8 — create a ticket after exact-payload approval

Implemented in commit `443b0ad` (merged as PR #10): frozen Jira create
payloads, human approvals and one-use execution with timeout reconciliation.
`ticketing/approvals.py` exposes `TicketApprovalService`; the flow lives
behind loopback-only web endpoints (the chat loop stays read-only):

- `POST /tickets/drafts` — renders the Week 7 template into a payload,
  appends a unique correlation marker to the description **and** as a label,
  and stores the immutable payload with its SHA-256 hash. The response is
  the preview the human reviews.
- `POST /tickets/drafts/{id}/approve` — a 15-minute approval pinned to the
  payload hash, recorded with the approver's identity.
- `POST /tickets/approvals/{id}/execute` — checks approver identity and
  expiry, re-checks the draft's hash (any edit voids the approval), records
  an `executing` row, revalidates live createmeta/permissions
  (`validate_create_fields`), creates exactly once, verifies via read-back,
  and reconciles lost responses by searching for the correlation marker:
  found ⇒ `succeeded/reconciled`, not found ⇒ `outcome_unknown`. It never
  retries a create. A repeat execute returns the recorded outcome
  (`ticket_executions.approval_id` is UNIQUE).

All endpoints gate on the `approval_user` session (403 otherwise) and
return 409 when the local database is absent.

## Verification evidence

- `tests/test_ticketing.py`: exact-payload create (sent bytes == approved
  payload), idempotent double-click, wrong-approver and expired-approval
  rejection, marker reconciliation without retry.
- `tests/test_webapp.py`: full draft→approve→execute flow over HTTP,
  403 without the approval session, 409 without the database, 400 for
  malformed bodies.
- `tests/test_storage.py`: migration contract check plus a gated round-trip
  of draft/approval/execution rows against real PostgreSQL, including the
  one-execution-per-approval uniqueness.
- `tests/test_jira_client.py`: create posts exact fields and validates
  metadata before any HTTP.

## Deployed and exercised live (2026-10-02)

- Migrations `003_ticket_approvals.sql` (and Week 9's `004`) applied to the
  pilot database via the `scrum-agent migrate` runner — they had not been
  applied live before; the tables now exist in `scrum_agent`.
- Backup/restore drill for approval and execution records: `pg_dump` of the
  pilot DB (2.5 MB, 2,607 lines) restored cleanly into a scratch database —
  all four migrations recorded, all 17 tables with identical row counts
  (256 issue snapshots, 1,285 events intact). A second drill with sample
  draft/approval/execution/update-proposal rows in scratch databases
  confirmed every approval-record row survives dump→restore bit-for-bit.
  Scratch databases and dump files were removed afterwards; the pilot DB was
  only modified by the additive migrations above.
