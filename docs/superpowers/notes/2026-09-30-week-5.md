# Week 5 implementation note

Week: 5 — Generate a useful current-sprint report
Goal: "I can generate and export a report for my current sprint."
Implementation date: 2026-09-30
Decision: **complete pending pilot-user demo** — all deliverables are
implemented and verified against the checked fixture dataset and live
Jira/PostgreSQL (evidence below); the pilot user's own Friday demo (generate a
report for the real board, verify totals manually, export) remains.

## What was built

| Deliverable | Implementation |
|---|---|
| Metrics from persisted inputs | `reports/metrics.py`: `build_report` computes current scope, per-status counts (done via the board's mapped done-status **IDs**, never the name "Done"), configured estimates (missing = unknown, never zero; done/not-done/total), and explicit blockers only (`blocked` label or blocks-issue link) — all from Week 4 snapshots plus the versioned board configuration. ADR-0002's current-state subset; commitment/scope-change metrics are carried as explicitly unavailable (Week 6 changelog analysis), and sprint-goal achievement is always "unknown (human-confirmed)". |
| Narrative | Deterministic template over the computed fields: goal line, scope/status summary, estimate coverage, explicit blockers or an accurate "none flagged", decisions-needed (unassigned unfinished, missing estimates), completeness + freshness, and the historical-unavailability caveat. Every sentence traces to a stored field; no model output enters the durable report. |
| Selection/view/export | Web `/reports`: sprint selector (active+future), job status page with htmx auto-refresh, HTML-escaped report view (totals table, issue table with links, narrative), Markdown/CSV downloads of the **same** report object. `reports/exports.py`: CSV cells starting with `=`, `+`, `-`, `@`, tab or CR get the `'` guard; Markdown cells additionally escape pipes/backslashes and flatten newlines. Freshness, estimate coverage and a completeness label (complete/partial + named notes) appear in the view and both exports. |
| Asynchronous durable jobs | `migrations/002_report_jobs.sql`: one `report_jobs` row per report, `request_key` = sha256(board, sprint, cutoff hour) UNIQUE → duplicate delivery returns the existing job; status machine queued→running→done/error with attempts. `reports/jobs.py`: `ReportJobs.submit` (resolves the sprint scope-checked, estimates duration from stored issue count), `run_once` claim (requeues `running` orphans first — restart recovery), `execute` (build + store the report JSONB on the row; failures recorded as `error` + message, never raised). The web process runs a background worker task; the CLI runs the worker inline; agent tools `build_sprint_report`/`get_report` only submit and poll — no blocking tool call in the conversation loop. Verified for duplicate delivery, kill-style restart (orphan requeued, attempts=2, completes) and error capture; gated round-trip on real Postgres. |
| Access revalidation | Execution performs **one** scoped live search (`sprint = <id>`) after reading stored snapshots; membership comes from the persisted greenhopper `sprint` field. Stored issues absent from the live result — revoked access, removed from sprint, deleted — are excluded from details **and** totals, named in the completeness notes, and flip the report to `partial`. Whole-scope denial fails the job closed (typed Jira error). |

Fixture additions (`tests/checked_queries.py`): status IDs, story-point values,
the greenhopper sprint field and a `blocked` label — the checked dataset now
yields hand-computable report truth (sprint 78 = PAY-1 3 pts blocked / PAY-2
2 pts done / PAY-3 unknown).

## Verification evidence

- Full suite: **329 passed + 1 skipped** (`pytest`), `ruff check .` and
  `ruff format --check .` clean. No live Jira in tests. The skip is the gated
  DB round-trip, which passes with `SCRUM_AGENT_TEST_DATABASE_URL`
  pointed at the disposable `scrum_agent_test` database.
- Checked dataset: report totals match hand-computed expectations
  (scope 3, done 1, estimates 5/2/3, coverage 2/3, blockers PAY-1,
  completeness complete); revoked-PAY-1 variant recomputes to scope 2 /
  estimates 2 with `partial` + named exclusion.
- Exports: `=1+1 | @SUM(A1)` summary exports as `'=1+1 \| @SUM(A1)` in
  Markdown and a guarded quoted CSV cell; totals rows identical to the report
  object in both formats; web view escapes `<script>` issue summaries.
- Live (real Jira GACD + week-4 PostgreSQL, 2026-09-30): `migrate` applied
  `002_report_jobs.sql` once; two `collect --full` runs re-reconciled all 256
  issues (262 pages each) — the first because the stored snapshots predated the
  sprint-membership fields, and the report correctly refuses to invent
  membership from thin data. Live report for closed sprint 75203
  ("2025 CDCP&CMIR S17"): scope 10, done 10, 29 points across 5 estimated
  issues with 5 explicitly unknown, zero blockers, completeness complete,
  freshness "0m ago" — cross-checked against `scrum-agent search --sprint
  75203` (10 issues) and the board's own sprint listing. A second
  `report` run for the same cutoff hour reused job 1 ("reusing the existing
  job") — persisted-job idempotency holds on real data. `--format csv --out`
  wrote matching totals; the served `/reports` pages rendered the stored
  report, totals and both export links over loopback.
- Design notes: the job row *is* the report record (spec §4 identity fields
  live in the stored JSONB, including site/board/sprint/goal/timezone/cutoff/
  generated/metric-policy version/completeness); the report is never
  recomputed on export — exports render the stored object, so a narrowed
  permission set can never silently reuse a wider report.
- Scope-model correction (found live): board 23031 lists sprints that
  **originate on board 6603** — Jira's board/sprint endpoint is the authority,
  so the Week-2 `origin_board_id == board_id` check rejected the pilot board's
  own sprints (`scrum-agent sprints` over all states failed live). Sprint scope
  is now "listed by the configured board" (`get_sprint` verifies listing
  membership; the origin check is gone); issue data stays hard-scoped to the
  pilot project on every JQL search, so nothing else loosened. Sprint
  membership is read from `customfield_10020` (object array) as well as the
  legacy greenhopper `sprint` string field, since the pilot site uses the
  former. Week 2's checked queries and tests were updated to the corrected
  model.
