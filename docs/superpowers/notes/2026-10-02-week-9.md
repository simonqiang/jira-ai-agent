# Week 9 — updating tickets without losing unrelated edits

Implemented reviewed field-level updates on top of Week 8's
approve-execute-once machinery. `ticketing/updates.py` introduces
`TicketUpdateService` with three operations, exposed as loopback-only web
endpoints beside the Week 8 create flow (the chat loop stays read-only):

- `POST /tickets/updates` — fetches the live issue (scope-checked by the
  Jira client) and diffs the requested values against it. Only fields whose
  value actually changes enter the proposal; a no-op request is rejected.
  Unknown fields, non-string values, malformed dates and labels with spaces
  fail validation before anything is stored. Supported fields: `summary`,
  `description`, `acceptance_criteria` (`customfield_10350`), `labels`,
  `due_date` — one `_UPDATABLE_FIELDS` entry each, mirroring the fields the
  pilot reads.
- `POST /tickets/update-proposals/{id}/approve` — a 15-minute approval pinned
  to the proposal's payload hash, identical in shape to Week 8.

## The safety chain

1. **Stale rejection before any write.** Every field the proposal changes is
   compared against the value the reviewer saw (`base`). Any drift ⇒
   `rejected_stale` with per-field conflicts; nothing is sent to Jira. The
   stale proposal's approval can never execute later — the execution row is
   already recorded and a repeat execute returns that recorded outcome.
2. **Unrelated edits survive.** Edits to *other* fields do not block the
   write, and because only the reviewed fields are PUT to Jira, concurrent
   work by someone else is never part of our payload.
3. **Post-write verification.** The issue is read back and every requested
   value is checked. All match ⇒ `succeeded`; a 204 that did not stick ⇒
   `verification_failed`; a failed PUT whose values did not land ⇒ `failed`.
   None of these claim success.
4. **Reconciliation, not blind retry.** If the PUT errors after landing
   (timeout past the server applying it), the read-back decides: values
   present ⇒ `succeeded` with `reconciled: true`. Updates are idempotent, so
   unlike Week 8 no correlation marker is needed — the read-back is the
   reconciliation.
5. **Audit trail.** `scrum_agent.ticket_update_executions` stores the
   requested changes, the verified per-field outcome, status and timestamps.
   Migration `004_ticket_updates.sql` adds the proposal/approval/execution
   tables with the same one-execution-per-approval uniqueness as Week 8.

## Documented residual race

Jira Cloud REST has no atomic precondition on issue updates (no
If-Match/ETag). An external edit landing between the pre-write re-read and
the PUT could still be overwritten; the window is seconds, the changelog
keeps both edits visible, and the pilot accepts this rather than faking a
guarantee. Documented in the module docstring and README.

## Verification evidence

- `tests/test_ticketing_updates.py`: diff contains only changed fields;
  unknown/no-op/bad-value rejection; stale rejection leaves Jira untouched;
  an unrelated concurrent edit proceeds and is preserved; write error that
  lands reconciles to `succeeded`/`reconciled`; write error that never lands
  and a silent non-sticking write both refuse to claim success; idempotent
  double-click; wrong approver and expired approval.
- `tests/test_webapp.py`: full propose→approve→execute flow over HTTP with
  exactly one PUT carrying only the reviewed field; intervening edit to the
  reviewed field returns HTTP 409 `rejected_stale` with no PUT; 403 without
  the approval session, 409 without the database, 400 for invalid bodies.
- `tests/test_jira_client.py`: `update_issue` PUTs exactly the given fields,
  accepts a 204, rejects an unexpected body and refuses out-of-scope keys
  before any HTTP.
- `tests/test_storage.py`: migration contract check plus a gated round-trip
  of proposal/approval/execution rows against real PostgreSQL (jsonb
  round-trip, one-execution-per-approval uniqueness).
- Full suite green, `ruff check .` and `ruff format --check .` clean.
